A malformed element name is refused, not reinterpreted

ElementName::parse read its numeric header with sscanf("%llu.%llu#%llu")
and its parent digests with an unchecked from_chars. Both report success
while ignoring whatever follows what they understood, and both results
were cast straight into narrower fields.

So `P4294967296.0#0` parsed as feature serial 0. Not as garbage, and not
as a failure, as a valid name for a different, real element. That is
the failure ADR 0005 exists to prevent, arriving through the file reader
rather than through geometry: a reference that silently means the wrong
face is worse than one that fails.

It matters because these strings are not all ours. parse is fed from
saved documents, from DDC cache blobs, and across the C ABI from plugins
and from the iPad shell, so some of this input is genuinely untrusted.

Six things were accepted that toString cannot produce:

  * numbers past the width of the field they were assigned to, silently
    truncated, featureSerial is 32 bits, opTag 16, discriminator 32;
  * a numeric header followed by anything at all, since sscanf checked
    only that three conversions succeeded;
  * a parent list that was never closed;
  * a parent digest of any length, because from_chars stops at the first
    character it cannot use and calls that success, so a truncated
    digest read back as a smaller number;
  * an empty parent list, which the writer never emits;
  * empty path components, so `P1.0#0`, `/P1.0#0`, `P1.0#0/` and
    `P1.0#0//P2.0#0` were four spellings of one name and the format had
    no single one.

parse is now a strict inverse of toString: exact separators, numeric
fields that must fill their span and fit their width, parent lists closed
at the end of the step, digests of exactly the sixteen hex digits the
writer emits, and no empty components. Nothing in the suite changed
behaviour, because everything stored was written by toString; what
changes is what happens to text that was not.

Callers already handle this correctly, DocumentStore turns a null name
into "this document contains a geometric reference we cannot read", so
strictness surfaces as a legible message rather than a wrong reference.

tests/acceptance/element_name_parse.cpp states each refused form
alongside the name the old parser invented for it, and every check is
verified by breaking it: range (3 failures), trailing junk (2),
unterminated list (1), digest length (2), empty components (3).

The unterminated-list case needed a second example to catch at all. The
list's length is computed assuming the last character is the closing
bracket, so with one stray character after sixteen valid hex digits the
window lands exactly on those sixteen and the stray one is dropped:
`P1.2#3[0123456789abcdefz` read back as a perfectly good name. The
obvious test missed it because the digest-length check happened to catch
the shorter case, and the mutation is what found the gap.
